# Phase 3: Event Store + Photo Store + Event Coordinator (FSM) - Context

**Gathered:** 2026-10-10
**Status:** Ready for planning

## Phase Boundary

Каждое подтверждённое открытие шлагбаума превращается ровно в одну запись в SQLite с фото-доказательствами на диске; OCR вынесен в отдельный поток с ограниченной очередью и не блокирует захват и запись. Схема БД не зависит от OCR-провайдера. Эта фаза НЕ включает детекцию автомобиля (Phase 4), реальный OCR-провайдер (Phase 5) и автозапуск (Phase 6).

## Что уже решено ранее (не переспрашивать)

- **Два шлагбаума, по камере на каждый; каждая камера эмитит своё событие** (владелец, 2026-10-06). Дедупликация событий — внутри камеры; между камерами её нет.
- **Источник событий:** `BarrierConsumer.transitions` (`TransitionEvent`, `emits_event=True` только на подтверждённом OPEN, re-arm защищает от дублей; 02-02-SUMMARY).
- **Задержка события 8–16 с после ухода стрелы** — следствие обновления картинки камеры раз в ~8–9 с, а не дефект. Детектор считает `dwell` по уникальным картинкам (`PictureDedup`).
- **Стек:** SQLite (stdlib), фото файлами, в БД путь (PROJECT.md, REQUIREMENTS STORE-01/02).
- **OCR-провайдера нет** до Phase 5: до него работает заглушка.

## Implementation Decisions

### Фото-доказательства
- **D-01:** Для каждой камеры в памяти хранится кольцо последних ~6 УНИКАЛЬНЫХ картинок (≈48 с при обновлении раз в 8 с). Повторы одной картинки в кольцо не попадают (использовать `PictureDedup`).
- **D-02:** При событии сохраняется до 4 файлов: 3 картинки ДО открытия (когда машина стоит у закрытой стрелы, номер читается лучше) и картинка подтверждения. У события одно «главное» фото (путь в `events`), остальные в таблице `event_photos`. Какой кадр лучший для OCR выбирает Phase 4.
- **D-03:** Фото сохраняются синхронно с записью события (до постановки в очередь OCR), чтобы кольцо не успело перезаписаться.

### Запись события
- **D-04:** Записью считается только ОТКРЫТИЕ (тип `open`). Закрытия не пишутся.
- **D-05:** Время хранится двух видов: `opened_at` (первая картинка без стрелы) и `confirmed_at` (момент подтверждения детектором). Обе в UTC ISO; `camera_id` обязателен.
- **D-06:** Поле номера `plate` = NULL и `ocr_status` (`pending` / `done` / `unreadable` / `no_provider`) описывает состояние распознавания; схема не знает о конкретном OCR-провайдере (STORE-04), провайдер пишется строкой в отдельное поле.

### Очередь OCR и сбои
- **D-07:** Порядок: сначала запись события и фото в БД (`plate=NULL`, `ocr_status=pending`), потом в очередь OCR ставится только `event_id`. Захват и запись никогда не ждут OCR.
- **D-08:** Очередь ограниченная (размер по умолчанию 10). При переполнении запись остаётся `pending`, фоновый проход подбирает её позже; при перезапуске сервиса все `pending` пере-ставятся в очередь.
- **D-09:** Пока провайдера нет, заглушка помечает записи `no_provider`; ничего не теряется и не блокируется.

### Хранение
- **D-10:** Раскладка: `data/events/ГГГГ-ММ-ДД/cam_N/<время>_<id>.jpg`, JPEG качество 90, полный размер кадра.
- **D-11:** Автоудаления нет. При старте сервис пишет в лог занятый объём каталога фото и размер БД (для аудита, ничего не чистим).

### Claude's Discretion
- Схема таблиц, имена колонок, миграции, индексы и уникальный ключ дедупликации (STORE-03), например по (`camera_id`, `opened_at`).
- Устройство колец и потоков: один писатель SQLite, режим WAL, как консьюмер передаёт событие координатору.
- Формат id, кодирование времени в имени файла, поведение при ошибке записи фото/БД (громко логировать, не падать).
