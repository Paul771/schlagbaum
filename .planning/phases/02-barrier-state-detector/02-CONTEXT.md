## Implementation Decisions

### Источник данных — КРИТИЧНО (установлено эмпирически, живые замеры 2026-10-04)

- **D-01:** `preview.mp4` — это НЕ видеопоток, а одно-кадровый снимок: ffmpeg сообщает `Duration 00:00:00.04` и отдаёт ровно 1 кадр (1280×720, h264). Ровно то же поведение у `files/proxy.php?link=…&token=…`.
- **D-02:** Живого потока в веб-интерфейсе нет. Страница `video-control.php` содержит только 2 URL `preview.mp4`; ни `.m3u8`, ни `rtsp`, ни `rtmp` не найдены.
- **D-03:** Реально доступный темп — ~1.5 кадра/с на камеру при ПАРАЛЛЕЛЬНОМ поллинге обеих камер (30+30 кадров за 20 с). Потолок задаёт сервер (~0.4–0.7 с на снимок), а не клиент.
- **D-04:** Следствие: открытие шлагбаума (2–5 с) даёт ~3–8 кадров. Детекция строится на **классификации состояния с dwell-подтверждением**, а не на непрерывном отслеживании перехода. SC #1 читается как «состояние подтверждено N кадрами», а не как трекинг скорости.
- **D-05:** Захват идёт через `capture_mode: "snapshot"` (`src/capture/snapshot.py`) — HTTP GET снимка + декод в процессе через OpenCV. Спавн ffmpeg не требуется. Реальный выигрыш: 0.79 → 1.50 fps на камеру.
- **D-06:** HTTP keep-alive обязателен. Одна `requests.Session` живёт весь цикл камеры; пересоздание соединения или re-login на каждый кадр стоит в ~3.5 раза дороже (1.45 с против 0.41 с). `Connection: close` — никогда.
- **D-07:** ffmpeg-путь (`capture_mode: "ffmpeg"`) сохранён как фолбэк и остаётся покрыт тестами супервизора. Он полезен, если источник когда-нибудь станет настоящим потоком.
- **D-08:** Валидация (SC #4) обязана опираться на РЕАЛЬНЫЕ записи: реальное открытие шлагбаума и реальный проезд машины при закрытом шлагбауме. Синтетика приемлема только как дополнительный regression-фикстур. Запись — через `scripts/record_validation.py` в `data/recordings/<label>/` (каталог gitignored).

### Потребление кадров
- **D-09:** Детектор — потребитель `FrameBuffer.pop()` (документированная точка интеграции Phase 2 в `src/main.py`). Снимки тегируются `camera_id` при помещении в буфер.

### Claude's Discretion
- Метод детекции: фоновое вычитание (MOG2) в ROI / контурная геометрия штанги / энергия движения / разница с фоновым кадром.
- ROI: ручные координаты на камеру в `config.json` / авто-обучение / всё изображение.
- Конкретные значения dwell (сколько кадров подтверждают состояние), порогов и backoff.
- Роль двух камер: обе детектят / одна основная + вторая резерв / независимо со сводом.
- Стратегия при «неизвестном» состоянии между подтверждениями.

## Specific Ideas

- Шлагбаум — для жителей двора, кадры 1280×720, камеры смотрят со сторон. Ночные сцены с ИК-подсветкой и переключением day/night — отдельный класс ложных срабатываний.
- Нужны сценарии записи: закрыт/покой, открытие, открыт, закрытие, машина при закрытом шлагбауме, машина при открытом, ночь/смена освещения.

## Existing Code Insights

### Reusable Assets
- `FrameBuffer` — bounded drop-oldest, уже тегирован по `camera_id`, покрыт тестами.
- `SnapshotPoller` — готовый источник кадров с re-auth и backoff.
- `scripts/record_validation.py` — запись реальных сценариев с манифестом.
- `scripts/probe_snapshot_capture.py` — живой замер фактического fps по обеим камерам.

### Established Patterns
- Секреты только в `.env`, не-секретные настройки — в `config.json`.
- Инъекция `clock`/декодера для тестов без сети.
- Логирование с префиксом `camera=<id>`, токен и PHPSESSID маскируются.
