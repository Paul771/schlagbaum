<objective>
Turn the proven signal into a correct state machine, and prove with pure ratio sequences that the four transitions are the only transitions.

Expansion from 02-01's tracer: the one-path FSM becomes a two-sided hysteretic machine with a dead band, frame-count confirmation, and edge-only emission. Then seven tests — driven by hand-authored ratio sequences with no images at all — pin down the transition sequence, duplicate suppression, and false-positive resistance for both the passing-car and lighting-swing cases.

Purpose: BARRIER-03 and BARRIER-04 are the requirements that fail silently. A machine that reports a state correctly but emits a spurious second event on every opening looks healthy in a log until an auditor counts the events. These tests are the only thing standing between the ratio signal and that failure, so they are written as pure functions of a ratio sequence — deterministic, instant, and readable as a specification of the machine's behaviour.

Output: a complete `src/detect/fsm.py`, a frame-to-transition convenience method on `BarrierDetector`, and `tests/test_barrier_fsm.py` with all seven tests green.
</objective>

## Why these tests are pure ratio sequences

RESEARCH's Pitfall 3 is that an FSM tested only through rendered frames cannot distinguish a state-machine bug from a rendering bug. Feeding the machine a literal list of floats removes the image layer entirely, so a failure here unambiguously means the machine is wrong. It also makes these tests instant and byte-stable — the fastest feedback available in the phase.

  <action>
Write the three tests first and confirm test_full_cycle_transitions fails against 02-01's minimal FSM.

Implement the machine with two-sided thresholds and a dead band. Going from CLOSED toward OPEN requires the ratio to fall at or below release and to do so for confirm consecutive frames. Going from OPEN toward CLOSED requires the ratio to reach or above seat for confirm consecutive frames. A ratio strictly between release and seat is the dead band: it holds the current state and clears BOTH counters, so partial progress toward either threshold cannot accumulate across an intermediate sample. This is the rule RESEARCH is explicit about, and Test 2 is what enforces it.

**Test 1's run lengths are load-bearing — state them as confirm+1, not as a literal two.** With confirm=2, CLOSED->OPENING fires on the second consecutive open-ish sample, and OPENING->OPEN needs a *third* ratio below release (the OPENING branch evaluates the current sample after the counter has already fired). A two-and-two sequence therefore yields CLOSED->OPENING, OPENING->CLOSED, CLOSED->OPENING, OPENING->CLOSED and never reaches OPEN — simulated against this exact machine during revision. Three per direction yields the asserted four edges; four and five also do. Express the run length as `confirm + 1` in the test so it stays correct if confirm is ever re-fitted (the research explicitly offers a larger confirm as the easiest knob if real footage proves noisier).

**Test 2's input must distinguish the correct machine from a broken one.** The dead band's whole job is clearing both counters, and only an input where an un-cleared counter would change the outcome can prove it. `[open-ish, MID, open-ish, open-ish]` does exactly that: correct — one counter cleared at the MID sample, the two surviving open-ish samples fall short of confirm, so the machine emits CLOSED->OPENING only; broken (counters not cleared) — the MID sample is skipped and three open-ish samples accumulate, emitting CLOSED->OPENING *and* OPENING->OPEN. Verify both directions by simulating the broken variant, and keep the assertion an exact-length equality on the transition list. Do not substitute a sequence whose dead band is sandwiched between two closed-ish samples: that sequence returns an empty transition list under both the correct and the broken machine, so it proves nothing.

Transition records must be edge-only: step returns a transition only when the state actually changes, and returns a no-transition result otherwise. That contract is what makes BARRIER-03 hold downstream — a caller that logs on every step call would emit duplicates, so the machine must not hand it a change record for an unchanged state.

Every transition record carries the frame index passed to step. Do not introduce any time source. Two runs over the same sequence must produce identical output objects, which test_confirmation_is_frame_counted relies on.

Model "partially open" per RESEARCH Open Question 2: it is not a fifth state. Expose it as a derived boolean computed from the current state (true while in OPENING or CLOSING) rather than as a stored state, so the machine stays four-state while BARRIER-01's three-way report remains expressible.

Keep the module free of type hints, matching the rest of the codebase, and reuse the existing logger rather than adding a second one.
