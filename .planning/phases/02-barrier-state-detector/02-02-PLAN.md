<objective>
Wire the barrier detector into the running service and validate it against real recorded footage.

Purpose: close BARRIER-01..04 empirically, above all SC #4 — "Barrier detection is validated against recorded real footage of both a genuine opening and a car passing with the gate closed."

This plan is gated on a human recording session. `data/recordings/` is empty and the required footage cannot be synthesised: someone has to physically open the barrier and drive a car past it. Plan 02-01 deliberately delivered the classifier and FSM without any of that, so this plan is where reality enters — and where `margin`, dwell and the ROI coordinates get their final calibration.

Phase 2 persists nothing. The consumer exposes `current_state` and an emitted-transition counter; Phase 3's event store reads those.
</objective>

  <action>
    **GATE: do not start until `data/recordings/` contains at least a closed and an open (or opening) session for each camera.** If it does not, stop and report the missing labels rather than inventing references.

    Create `scripts/build_references.py`:
    1. Scan `data/recordings/*/manifest.json`, group frames by session `label` and `camera_id`.
    2. For each camera and each lighting bucket (`day`/`night` via `bucket_for(mean_brightness(frame))` from `src.detect/barrier.py`), pick one clean `closed` frame and one clean `open` frame — choose the frame whose edge map is most typical for its class (lowest median distance to the other frames in that class), so a mid-transition frame or one with a car in it is never chosen as the reference.
    3. Compute the two ROIs per camera: the `closed` ROI is the bounding box of the arm's edge pixels in the closed frame, the `open` ROI the equivalent in the open frame. Print both and allow an operator override via `--roi-closed x,y,w,h` / `--roi-open x,y,w,h` — the human look matters more than the automation here.
    4. Preprocess through `src.detect.barrier.preprocess` and write reference maps at `WORK_SIZE` to `data/references/<camera_id>/<bucket>/{closed,open}.png` (gitignored) plus a `rois.json`.
    5. Also write a small COMMITTED fixture set: a handful of representative frames per class downscaled to 320×180 JPEG (quality ~80) into `tests/fixtures/barrier/<class>/<camera_id>/<n>.jpg` with `tests/fixtures/barrier/index.json`. Keep it to ~5-10 frames per class per camera so the repo stays small; the full recordings stay local.
  </action>

  <name>Task 2: Consumer thread and main.py wiring</name>
  <files>
    src/detect/consumer.py
    src/main.py
    config.json
    tests/test_detect_consumer.py
  </files>
  <action>
    1. Create `src/detect/consumer.py` with `class BarrierConsumer`:
       - `__init__(self, camera_id, frame_buffer, detector, fsm, stop_event)`;
       - `run()` loops popping frames and driving the detector + FSM, accumulating `self.transitions` (list of `TransitionEvent` with `emits_event=True`) and `self.current_state`;
       - **The `FrameBuffer.pop()` call blocks forever on an empty queue** (`queue.get()` with no timeout). The consumer MUST therefore be its own thread and must stop via `stop_event` — do not make `main.py` pop inline, and do not add a busy-poll loop. If a bounded wait is needed, pop in the consumer thread and check `stop_event` between frames;
       - a detector exception must be logged and must NOT kill the thread (a malformed snapshot must not stop detection) — same resilience rule as the capture supervisor.
    2. Extend `config.json` with a `"barrier"` block: `enabled`, `references_dir`, `rois_file`, `margin`, `dwell_open`, `dwell_closed`, `bucket_threshold`. Leave `capture_mode` and `snapshot_fps` untouched — they are verified (RESEARCH.md).
    3. Wire `src/main.py`: when `barrier.enabled` is true and references load successfully, start one `BarrierConsumer` daemon thread per camera over the buffers it already creates, and log `barrier consumer started for camera=<id>` alongside the existing capture-thread log. If references are missing, log a clear actionable message naming the bootstrap script and continue capturing — detection must never take capture down with it.
    4. Add `tests/test_detect_consumer.py` (no network): feed a fake FrameBuffer and a stub detector; assert frames are drained in order, `current_state` advances, and a raising detector does not kill the loop.
  </action>

  <name>Task 3: Validation harness and measured false-positive rate</name>
  <files>
    scripts/validate_barrier.py
  </files>
  <action>
    Create `scripts/validate_barrier.py`, the script that turns SC #4 from a claim into a number.

    1. Load `ReferenceSet` + ROIs produced by Task 1.
    2. Replay each recording session in timestamp order per camera: read the frame, `classify()`, feed the `BarrierFSM`, and collect transitions with `emits_event=True`.
    3. Compare against the session label and report:
       - **false openings** — open events committed in `closed_idle` and `car_passes_gate_closed` (the BARRIER-04 gate; must be 0), and **false-openings-per-hour** extrapolated from the replayed duration;
       - **detection latency** — for `opening`/`open` sessions, the number of samples between the first frame labelled as part of the opening and the committed `OPEN`;
       - **misses** — openings present in the recording but never detected;
       - per-bucket breakdown (day vs night) so an IR-switch failure is visible rather than averaged away.
    4. Exit non-zero if any false opening occurred, or if a genuine opening was missed, so the script is usable as a gate rather than a report nobody reads.
    5. If a metric fails, do NOT paper over it by loosening `margin`/`dwell` blindly: report the offending session and frame indices first. Widening the margin until nothing triggers is the classic way to make this detector useless.
    6. Paste the final numbers into `.planning/phases/02-barrier-state-detector/02-02-SUMMARY.md` under a "Measured validation" heading.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `data/recordings/` → validation replay | operator-recorded footage; labels are human-assigned and can be wrong |
| `data/references/` → runtime detector | generated once, then reused for the lifetime of the deployment |
| FrameBuffer → consumer thread | capture keeps producing while detection consumes; a slow consumer must not block capture |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-05 | Denial of service | `BarrierConsumer` | medium | mitigate | `FrameBuffer.pop()` blocks; the consumer must be its own thread and must never be called inline from `main.py`, or capture stalls behind detection |
| T-02-06 | Repudiation | recorded labels | medium | accept | Labels are human-assigned; the harness reports per-session numbers so a mislabelled session is visible rather than silently averaged |
| T-02-07 | Tampering | `data/references/` | medium | mitigate | References are regenerated by an explicit script and kept under gitignored `data/`; `load()` validates working size (T-02-01 from plan 02-01) |
| T-02-08 | Denial of service | detector raising | low | mitigate | A detector exception is logged and the consumer continues — one bad snapshot must not stop detection for the rest of the session |
</threat_model>
